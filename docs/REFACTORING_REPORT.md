# Отчет по рефакторингу ML-проекта

## 1. Цель работы

Цель рефакторинга - привести учебный ML-проект по прогнозированию временных рядов к более организованной и воспроизводимой структуре, близкой к требованиям production-разработки, не меняя смысл исследовательской части и результаты уже выполненных экспериментов.

Работа закрывает три пункта задания:

- рефакторинг кода ML-проекта под production-стандарты
- настройка Poetry, pre-commit и инструментов контроля качества кода
- интеграция локального виртуального окружения в рабочий процесс Git-репозитория

Основной принцип изменений - отделить исследовательский код в ноутбуках от повторно используемой логики приложения и сделать запуск проекта воспроизводимым на новой машине.

## 2. Состояние проекта до рефакторинга

До изменений проект уже содержал полноценную исследовательскую часть:

- EDA и подготовку временных рядов
- проверку стационарности
- статистические модели
- ML-модели
- DL-модели
- поиск аномалий
- итоговый baseline pipeline
- отчет с результатами экспериментов

При этом повторно используемая логика была в основном сосредоточена в `src/ts_pipeline.py`. Такой вариант удобен на этапе учебного прототипа, но при дальнейшем развитии проекта приводит к нескольким проблемам:

- загрузка данных, метрики, прогнозирование и запуск pipeline находятся слишком близко друг к другу
- сложнее тестировать отдельные части независимо
- сложнее переиспользовать функции в других точках проекта
- нет единого CLI для запуска pipeline
- зависимости устанавливаются без единого менеджера окружения
- проверки форматирования, линтинга и типов не выполняются автоматически
- виртуальное окружение не связано с конфигурацией проекта

Рефакторинг выполнялся без изменения исследовательских выводов и без переноса ноутбуков в production-код.

## 3. Новая структура Python-кода

Рабочая логика вынесена в пакет `src/time_series_project` и разделена по ответственности.

| Модуль | Ответственность |
|---|---|
| `data.py` | загрузка CSV, определение колонок, очистка, частота ряда и train/test split |
| `metrics.py` | расчет MAE, RMSE, MAPE и sMAPE |
| `forecasting.py` | baseline-прогнозы Naive, SeasonalNaive и Drift |
| `anomalies.py` | rolling z-score, STL residual и IsolationForest |
| `pipeline.py` | единый запуск baseline pipeline и сохранение результатов |
| `config.py` | параметры запуска и пути к артефактам |
| `logging_config.py` | общая настройка логирования |
| `exceptions.py` | собственные исключения для ошибок данных |
| `cli.py` | запуск pipeline из командной строки |
| `__main__.py` | запуск пакета через `python -m` |

Файл `src/ts_pipeline.py` сохранен как слой совместимости со старыми ноутбуками. Новый код и автоматические тесты используют установленный пакет `time_series_project`, как и положено для структуры `src-layout`.

Такой подход дает возможность рефакторить проект постепенно, без одновременной переработки всех исследовательских ноутбуков.

## 4. Что изменено в коде

### Разделение ответственности

Функции сгруппированы по назначению. Загрузка данных больше не смешивается с расчетом метрик или прогнозированием, а запуск pipeline не содержит реализацию всех вспомогательных операций внутри одного файла.

### Конфигурация

Параметры запуска собраны в отдельной конфигурации. Это уменьшает количество жестко заданных значений внутри функций и делает поведение pipeline понятнее.

### Работа с путями

Для путей используется `pathlib.Path`. Это упрощает работу проекта в Windows, Linux и macOS и делает код менее зависимым от ручной сборки строковых путей.

### Типизация

Для функций добавлены аннотации типов. Mypy проверяет основной пакет `src/time_series_project` и помогает находить несовместимые типы до запуска программы.

### Ошибки и исключения

Для ожидаемых ошибок данных используются собственные исключения проекта. Это делает ошибки более понятными и отделяет проблемы входных данных от случайных системных исключений.

### Логирование

Вместо разрозненного вывода состояния добавлена общая настройка `logging`. Pipeline сообщает основные этапы работы и при этом не зависит от ручных `print` в рабочей логике.

### CLI

Добавлена команда:

```powershell
poetry run ts-pipeline --data data/raw/international-airline-passengers.csv
```

Также пакет можно запускать как модуль Python:

```powershell
poetry run python -m time_series_project --data data/raw/international-airline-passengers.csv
```

CLI делает pipeline удобным для повторного запуска без открытия Jupyter Notebook.

### Комментарии и docstring

Добавленные комментарии и docstring написаны на русском языке. Комментарии используются там, где нужно пояснить назначение решения или неочевидную логику. Декоративные разделители в коде не используются.

## 5. Автоматические тесты

Для ключевой логики добавлен каталог `tests`.

Проверяются:

- загрузка и подготовка временного ряда
- расчет метрик
- baseline-прогнозы
- методы поиска аномалий
- полный запуск pipeline на тестовых данных

Локальный запуск:

```powershell
poetry run pytest
```

На момент подготовки рефакторинга тестовый набор содержит 13 тестов. Все 13 тестов проходят успешно.

## 6. Poetry и управление зависимостями

Зависимости проекта описаны в `pyproject.toml`.

Основные зависимости включают:

- NumPy
- pandas
- scikit-learn
- statsmodels
- matplotlib
- statsforecast
- mlforecast

Тяжелые DL-зависимости вынесены в отдельную необязательную группу `dl`:

```powershell
poetry install --with dev,dl
```

Для обычного запуска baseline pipeline достаточно:

```powershell
poetry install --with dev
```

Такое разделение позволяет не устанавливать PyTorch и NeuralForecast там, где они не нужны.

После разрешения зависимостей Poetry создает `poetry.lock`. Этот файл рекомендуется хранить в Git, потому что он фиксирует конкретные версии зависимостей и помогает воспроизводить одинаковое окружение на разных машинах.

## 7. Виртуальное окружение `.venv`

В `poetry.toml` задано:

```toml
[virtualenvs]
in-project = true
create = true
```

Поэтому Poetry создает виртуальное окружение непосредственно в корне проекта:

```text
project_neto_time_completion/.venv/
```

Сам каталог `.venv` не добавляется в Git. Он содержит платформозависимые бинарные файлы и может занимать большой объем.

В Git хранятся только файлы, необходимые для его воспроизводимого создания:

- `pyproject.toml`
- `poetry.lock`
- `poetry.toml`
- скрипты настройки проекта

`.gitignore` исключает `.venv/` из индекса Git.

Проверить используемое окружение можно командой:

```powershell
poetry env info
```

## 9. Pre-commit и контроль качества

В `.pre-commit-config.yaml` настроены проверки, которые выполняются перед коммитом.

### Базовые проверки файлов

Используются стандартные hooks:

- удаление пробелов в конце строк
- корректное окончание файлов
- проверка YAML
- проверка TOML
- поиск незавершенных merge-конфликтов
- защита от случайного добавления слишком больших файлов

### Ruff

Ruff используется как основной линтер Python-кода. Он проверяет типовые ошибки, импорты, упрощения кода и часть современных рекомендаций Python.

Запуск вручную:

```powershell
poetry run ruff check src tests
```

### Black

Black отвечает за единое форматирование Python-кода.

Проверка:

```powershell
poetry run black --check src tests
```

Автоматическое форматирование:

```powershell
poetry run black src tests
```

### Mypy

Mypy проверяет аннотации типов основного пакета:

```powershell
poetry run mypy src/time_series_project
```

### Pytest

Pytest выполняет автоматические тесты:

```powershell
poetry run pytest
```

## 10. GitHub Actions

В `.github/workflows/quality.yml` добавлена автоматическая проверка репозитория при `push` и `pull_request`.

CI выполняет:

1. получение репозитория
2. установку Python 3.11
3. установку Poetry
4. установку зависимостей
5. Ruff
6. Black в режиме проверки
7. Mypy
8. Pytest

Это позволяет находить проблемы качества кода не только локально, но и после отправки изменений в GitHub.

## 11. Что намеренно не менялось

Рефакторинг не должен подменять исследовательскую часть проекта, поэтому намеренно сохранены:

- Jupyter Notebook с экспериментами
- структура исходных данных
- сохраненные результаты исследований
- сравнение статистических, ML и DL-моделей
- основной исследовательский отчет `REPORT.md`
- старые импорты через `src/ts_pipeline.py`

`REPORT.md` отвечает на вопрос, какие модели исследовались и какие результаты получены. Этот документ отвечает на другой вопрос - как технически изменена структура проекта и процесс разработки.

## 12. Итоговая схема проекта

После рефакторинга проект разделен на несколько уровней:

```text
notebook/                исследовательские эксперименты
src/time_series_project/ повторно используемый Python-код
tests/                   автоматические тесты
scripts/                 установка и проверки качества
reports/                 результаты экспериментов
docs/                    техническая документация
```

Такое разделение сохраняет удобство учебного исследования и одновременно делает основной код более организованным, проверяемым и воспроизводимым.


Если все команды завершаются успешно, код, форматирование, типизация и тесты находятся в согласованном состоянии.
